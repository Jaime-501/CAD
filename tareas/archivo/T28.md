**Depende de:** T17, T20 (puede ejecutarse justo después de T22, antes de T23, para validar el backend completo antes del frontend)

**Objetivo:** Verificar el flujo completo sin UI, tanto en CI como contra la red real.

**Puedes tocar:** `internal/e2e/**`, `app_e2e_test.go` (raíz, paquete `main`), `*_e2e_integration_test.go`, `PROGRESO.md`, `docs/BITACORA.md`

**NO debes tocar:** `frontend/**`, código de producción (si un test necesita un cambio en producción, detente y repórtalo)

**Pasos:**
- **Versión offline (siempre se ejecuta):** un `httptest.Server` sirve un sitio falso completo (búsqueda, detalle, AJAX de episodios con CSRF, página de episodio, player y manifiesto HLS + un segmento). Flujo: `SearchAnime` → `GetAnimeDetails` (con streaming de episodios y eventos) → `GetVideoSources` → `SelectBestSource` → petición HTTP real **a través del proxy** (T19).
- El flujo que pasa por el núcleo de la app vive en `package main`, por lo que ese test va en la raíz (`app_e2e_test.go`). Los providers reciben la URL base del `httptest.Server`; el proxy se crea con la opción de red privada de pruebas activada (el `httptest.Server` escucha en 127.0.0.1). Esa opción **solo** se activa en tests.
- Comprobar además: la caché (T21) evita un segundo fetch; `SaveProgress`/`GetProgress` (T22) round-trip con un directorio temporal.
- **Versión real:** mismo flujo contra el sitio real bajo build tag `integration`, tolerante a cambios de contenido (asserts blandos, `t.Log` de lo encontrado).
- Validar URL HTTP/HTTPS y tipo reconocido en cada eslabón.

**Comprobación (docker compose run --rm app ...):**
- `gofmt -l .`, `go vet ./...` (y `-tags integration`), `go build ./...`
- `go test -race -count=1 ./...` (offline, sin red) pasa.
- `go test -tags integration ./... -run E2E -v` pasa localmente.
